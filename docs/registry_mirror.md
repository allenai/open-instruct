# Terminal-RL container registry mirror

How the Docker Hub pull-through cache that serves our Terminal/SWERL sandbox task images is stood
up, consumed, and warmed — written up as a handoff for a proposed move of the mirror off a Beaker
task and onto GCP. Everything below is the state as of 2026-08-06.

**Code locations** (all in `allenai/open-instruct`, branch `omni_agent`; `shatu/tmax` vendors a
byte-identical copy of `scripts/docker/` under `training/open-instruct/`):

| File | Role |
|---|---|
| `scripts/docker/launch_registry_mirror.sh` | Stands the mirror up as a Beaker experiment |
| `scripts/docker/warm_tmax_registry_mirror.py` | Pre-warms the cache from an HF dataset's image list |
| `docker/podman/setup_dockerio_mirror` | Runs **inside every training/eval job**; writes podman `registries.conf` from `$MIRROR_URL` |
| `scripts/docker/docker_login.sh` | Job entrypoint: calls the above, starts sharded podman services, writes Docker Hub creds |
| `Dockerfile` (lines ~98–126) | Bakes podman 5.6.2 / crun 1.14.3 + the config files into the training image |
| `open_instruct/environments/backends.py` | The actual `images.get()` / `images.pull()` per sandbox container |
| `scripts/data/build_tmax_images.py` | Builds & pushes the per-task images to Docker Hub (upstream of the mirror) |

---

## 1. What the mirror is today

A stock **`registry:3`** container running as a long-lived Beaker experiment on `ai2/jupiter`,
configured as a Docker Hub pull-through proxy:

```yaml
# generated by launch_registry_mirror.sh, stored as Beaker secret `registry-secret`,
# mounted at /etc/docker/registry/config.yml
version: 0.1
storage:
  filesystem:
    rootdirectory: /var/lib/registry      # <-- node-local, NOT a persistent volume
http:
  addr: :5000
proxy:
  remoteurl: https://registry-1.docker.io
  username: <docker hub user>
  password: <docker hub PAT>
```

Beaker task spec highlights:
- `hostNetworking: true` → it is addressed as **`<node-hostname>:5000`**, e.g.
  `jupiter-cs-aus-193.reviz.ai2.in:5000`. There is no stable DNS name or VIP.
- `context: {priority: urgent, minRuntime: 8h, autoResume: true}`
- Single replica. No TLS, no client auth, no persistent storage, no health check, no metrics.

### Consequences we live with
- **The endpoint moves whenever the task reschedules.** Every training/eval launch script hardcodes
  `--env MIRROR_URL=<host>:5000` at submit time, so the current host has to be re-derived before
  each launch (`beaker experiment get <mirror-workload> | .jobs[-1].node` → `beaker node get`).
  Historical hosts that are now dead: `-102, -112, -137, -150, -155, -193, -218, -219`.
- **`MIRROR_URL` is baked in at submit time.** A dead/stale mirror can only be fixed by relaunching
  the job — for a multi-day 32-GPU run that is expensive.
- **Cache is lost on every reschedule** (node-local `/var/lib/registry`), so a fresh warm is needed.
- We have seen a mirror serve **corrupt** manifests while still answering `/v2/` with 200 — a
  liveness check on `/v2/` is not sufficient, we have to probe a real task-image manifest.

## 2. How jobs consume it (podman path)

`scripts/docker/docker_login.sh` is sourced as the first thing in every training command. It:

1. Runs `/usr/local/bin/setup_dockerio_mirror`, which writes `/etc/containers/registries.conf`:

   ```toml
   [[registry]]
   location = "docker.io"

   [[registry.mirror]]
   location = "<MIRROR_URL>"
   insecure = true          # plain HTTP, no cert, no auth
   ```

   `MIRROR_URL` accepts a comma-separated list, so multiple mirrors can be tried in order.
   It also forces `storage.driver = "overlay"` and `[engine] num_locks` (default 8192, we run 65536).

2. Starts **`SWERL_PODMAN_SERVICE_COUNT`** podman `system service` daemons per node (we run 4–8),
   each with its **own graphroot/runroot** under `/var/lib/containers/storage/swerl-podman-shards/<n>`.
   → Each shard is an **independent image store**, so the same image is pulled once *per shard per node*.

3. Writes Docker Hub credentials into `~/.docker/config.json` from the `DOCKER_PAT` Beaker secret.

Then `open_instruct/environments/backends.py` does, per sandbox container:

```python
try:    self._client.images.get(image)      # local store hit
except ImageNotFound:
        self._client.images.pull(image)     # → mirror, else docker.io
```
gated by a cross-process file semaphore, `SWERL_DOCKER_START_CONCURRENCY=64` per node.

### The Docker Hub fallback mechanism
It is **podman's native behavior**, not custom code: for a registry with `[[registry.mirror]]`
entries, podman tries each mirror in order and, if all fail, falls through to the primary location
(`docker.io`) using the credentials from `~/.docker/config.json`.

Two things worth flagging to whoever builds the replacement:

- **The fallback is silent.** A dead mirror does not fail the job — it degrades to authenticated
  docker.io pulls, with a failed-connect + failover on *every* pull. We only notice via latency and
  Docker Hub rate limiting. Any GCP replacement should keep this property (soft-fail) but we would
  like it to be *observable*.
- **`docker login` is not enough for podman.** Podman reads `containers/auth.json`, not
  `~/.docker/config.json`, when pulling via its own socket. The eval path (`tmax`
  `scripts/beaker/run_eval_in_job.sh`) therefore does *both* `docker login` and `podman login`.
  A GCP registry requiring auth would have to be wired into both stores.

### Eval path
Terminal-Bench/harbor evals use the same mechanism: `beaker_configs/launch_eval.sh --mirror-url
HOST:PORT` → `--env MIRROR_URL` → same `setup_dockerio_mirror`. Harbor's `compose down --rmi all`
deletes each task image after every trial, so a 267-trial eval re-pulls ~267 images. Without the
mirror we blow through Docker Hub's unauthenticated 100-pulls/6h cap around trial 100 and 50–90% of
trials fail with compose errors — while still reporting a (silently low) pass@1.

## 3. Workload characteristics — sizing input

The images are **per-task**, not a handful of shared bases. From `allenai/tmax-15k-open-instruct`:

| Metric | Value |
|---|---|
| Dataset rows | 14,601 |
| **Unique images** | **14,490** |
| Repos involved | **1** — `hamishi740/swerl-tmax-v3`, one tag per task (content-hash tags) |
| Tags in that Docker Hub repo | 14,577 |
| Mean compressed image size | **~306 MB** (sampled 20; range ~215–530 MB) |
| Layer dedup across images | **only ~1.10×** (sampled 30 images: 9.80 GB of layers → 8.94 GB unique blobs) |
| **⇒ full warm cache size** | **~4 TB** |

The poor dedup is because `build_tmax_images.py` builds each task image from a Singularity-style
def with its own package installs; the shared `python:3.12-slim` base is a small fraction of each.

**Steady-state pull load (estimate, please sanity-check):** a 4-node run with
`num_unique_prompts_rollout=8` touches ~8 unique task images per training step. With
4 nodes × 4 podman shards = 16 independent image stores, that is up to ~128 pulls × ~300 MB ≈
**~38 GB pulled per step**, and steps are minutes. We also run an image janitor
(`SWERL_PODMAN_IMAGE_JANITOR_*`, prune unused images older than 10–30 min) because node disk fills
otherwise — which *increases* re-pull rate. Multiple concurrent runs + evals share the one mirror.

**Warming:** `warm_tmax_registry_mirror.py` enumerates images from the HF dataset
(`env_config.image` per row, plus `image.txt` files in the task-data tarball) and pulls each
through the mirror. Default method is `registry-api` (plain HTTP GETs of manifest + every blob, so
no local container runtime needed), 8 workers, `--platform linux/amd64`. Warming all 14.5k images
is a multi-TB, multi-hour job.

```
uv run python scripts/docker/warm_tmax_registry_mirror.py \
  --dataset allenai/tmax-15k-open-instruct --mirror <host>:5000
```

## 4. What we'd want from the GCP replacement

Roughly in priority order:

1. **A stable, long-lived endpoint** (DNS name) so `MIRROR_URL` stops being a per-launch,
   bake-at-submit-time liability. This is the single biggest win.
2. **Persistent cache storage** (~4 TB and growing) that survives restarts — no re-warm after every
   reschedule.
3. **Reachability from Beaker compute** (Jupiter primarily; Saturn jobs also reach the Jupiter
   mirror today, and we have runs on holmes/B300 nodes too), with enough bandwidth for the pull rate
   above.
4. **Health/observability** — an endpoint we can probe that distinguishes "up" from "up but serving
   corrupt manifests", ideally hit-rate and storage metrics.
5. **Auth story.** Today the mirror is unauthenticated plain HTTP (`insecure = true`) inside the
   cluster network. If the GCP endpoint needs credentials (e.g. Artifact Registry), we need a
   credential path that works for a **rootful podman `system service`** in a container — i.e.
   writing `containers/auth.json` (and `~/.docker/config.json`) at job start. That's a small change
   to `setup_dockerio_mirror` / `docker_login.sh` on our side; we just need to know the mechanism
   (static token in a Beaker secret vs. workload identity vs. `gcloud` credential helper).
6. **Keep the soft-fail-to-Docker-Hub behavior** — podman's mirror-then-primary fallback should
   still apply, so a mirror outage degrades a run instead of killing it.

Note: Artifact Registry **remote repositories** (upstream `docker.io`) look like a close match to
what we're doing, but the ~4 TB / 14.5k-tag working set and the fact that our own task images are
themselves hosted on Docker Hub are the two things worth checking against quotas. An alternative
worth discussing: push the task images to GCP **directly** from `build_tmax_images.py` rather than
to Docker Hub and then caching them back — that removes Docker Hub from the loop entirely.
