# Overfit diagnostic: Core and Megatron on 16 fixed GSM8K prompts

> Historical evidence. For current operating instructions, start at the [MILES guide](../index.md).

A positive update-correctness check: train repeatedly on a tiny fixed prompt set
through the fully asynchronous path and require training reward to rise. Both
arms rose. Neither reached 1.0 within 60 updates at the recipe learning rate.
This is a mechanics diagnostic, not a learning comparison or a throughput
qualification; see the limitations below.

Shared recipe: the full-SFT KDA/latent-MoE checkpoint used by the
[100-update comparison](gsm8k-results-20260911.md); three B300 GPUs per arm
(two EP2 trainers, one TP1 engine); 16 training prompts; 8 prompts x 4 responses
per update (32 samples), so each prompt recurs every second update and 30 times
over the 60 updates; LR 1e-6 constant, no KL, no GRPO std normalization,
clipping 0.2/0.28; 4096 response / 6144 context; greedy 32-row held-out at
updates 0/20/40/60; W&B `ai2-llm/olmo-rl-comparison` group
`overfit-gsm8k-20260915`. Each launcher selected its own 16 training and 32
held-out rows from seed 17, so the prompt sets differ between arms; the pass
criterion is per arm.

Both arms rise by about 0.12 (Core) and 0.05 (Megatron) from their first block
to their last, with response length and the truncation rate falling in step.
Per-batch reward tracks truncation closely on both arms: batches with 0-3%
truncated responses score 0.88-1.0, batches with 25-31% score 0.53-0.63. The
learned behaviour is finishing under the cap. Core reports group-level reward
statistics: groups with all-zero reward fell from 10.6% of groups (block 0-12)
to 1.1% (block 49-59) while all-one groups rose from 51% to 61%, leaving roughly
35-45% of groups carrying gradient throughout. Megatron does not log that
statistic.

## Trainer-side health

| Block | Core grad norm | Core train/rollout log-prob gap | Megatron grad norm | Megatron gap |
|---|---:|---:|---:|---:|
| 1-12 | 0.184 | 0.0085 | 0.899 | 0.0061 |
| 13-24 | 0.184 | 0.0100 | 0.559 | 0.0062 |
| 25-36 | 0.202 | 0.0100 | 0.381 | 0.0061 |
| 37-48 | 0.151 | 0.0094 | 0.237 | 0.0060 |
| 49-60 | 0.159 | 0.0096 | 0.224 | 0.0060 |

Both gaps stay far inside the 0.05 policy-drift bound; TIS clip fraction is
zero on both arms. PPO clip fraction and PPO KL are identically zero on both
arms because each collection receives one optimizer step and the old
log-probabilities are the same forward, so the objective reduces to centred
REINFORCE. Core's router auxiliary losses were flat (0.194 -> 0.193). The two
gradient-norm columns use each trainer's own reduction and are not comparable
across arms; Megatron's steady decay across the run is recorded, not explained.

Core's asynchronous path was genuinely exercised: average learner staleness
0.6-2.0 updates, 40-60% of responses spanned a policy publication
(`mixed_version_ratio`) from update 3 onward, and the completed queue dropped
0.9% of samples in the first block and none afterwards. Megatron ran at
staleness 1 with no rejected policy groups.

Same batch shape, prompt budget and GPU count. This reverses the direction of
the [September 11 timing](gsm8k-configuration-differences-20260911.md), where
Core's warm cycle was 1.33x Megatron's; the Core arm here uses packing, no
activation recomputation and the skipped scoring pass qualified on
[September 14](full-sft-basket-20260914.md), while the Megatron arm keeps the
r3 recipe (recompute on, 6144 context, no packing). Not a matched throughput
measurement.

## Limitations

- One seed per arm, different prompt sets, 32 samples per update. Block means
  are the readable signal; single updates swing by 0.3.
- The recipe learning rate was kept deliberately. Neither arm reached 1.0 in
  60 updates; the rise became visible only after about update 30. A faster
  learning rate would give a sharper diagnostic at the cost of comparability.
- Plain GSM8K at 0.8 initial reward is partly saturated for this checkpoint:
  half the groups were all-correct from the start and carried no gradient.
- Trainer-side entropy is not logged on the Core arm; Megatron's
  `entropy_loss` is zero because the entropy coefficient is zero.
