# Full FP32: a baseline for cached-inference precision

This frozen-weight experiment compares SGLang cached generation against Core
full-sequence scoring in BF16 and FP32. On the non-EMO checkpoint, moving both
forward paths to FP32 lowers mean absolute log-probability mismatch from
0.0241028 to 0.00000214616: **99.9911% lower, or about 11,231 times smaller**.
EMO improves from 0.0404259 to 0.00000255046: **99.9937% lower, or about 15,850
times smaller**. Its longer fixed-prefix control still has a localized residual,
described below. The result establishes a numerical target for selective-precision
work, not a measured improvement in RL reward. No backward pass or optimizer ran.

## Matched cached-generation comparison

Both serving arms use the eager Core-compatible reference. They start from the
same checkpoint values, prompts and sampling seed. Each arm generates four
64-token continuations, one each for math, code, ifeval and general. Core scores
each arm's actual tokens and causal prefixes. The continuations can differ
between precision arms; these are not identical-token paired cached trajectories.

All errors are absolute differences of natural log-probabilities.

| Checkpoint | Precision on both sides | Mean | p99 | Maximum | Ratios outside [0.8, 1.2] |
|---|---|---:|---:|---:|---:|
| Non-EMO | BF16 | 0.0241028 | 0.287354 | 0.433603 | 2.7344% |
| Non-EMO | FP32 | 0.00000214616 | 0.0000196457 | 0.0000233650 | 0% |
| EMO | BF16 | 0.0404259 | 0.325688 | 0.897077 | 4.6875% |
| EMO | FP32 | 0.00000255046 | 0.0000227571 | 0.0000271797 | 0% |

The ratio is `p_Core / p_serving`. Outside-20% frequency is not an observed PPO
clipping rate. There are only 256 generated tokens per checkpoint/precision arm,
so this is a short numerical baseline, not a long-context or tail-risk qualification.

## Identical full-prefix control

Both serving arms also prefill-score the same four saved 512-token continuations
from the earlier LM-head experiment: 2,048 identical response-token scores per
checkpoint. This separates full-prefix agreement from cached-decoding agreement.

| Checkpoint | Both BF16 mean | Both FP32 mean |
|---|---:|---:|
| Non-EMO | 0.000000435247 | 0.00000230487 |
| EMO | 0.0364178 | 0.00230531 |

Non-EMO BF16 already agrees closely when both frameworks use the full-prefix
reference path. Its material FP32 improvement is the cached-decoding comparison
above; its full-prefix numbers do not show a BF16 problem that FP32 needs to fix.
The cross-precision control is much larger: non-EMO BF16 serving versus FP32
Core has a full-prefix mean gap of 0.0316909. Merely changing one side to FP32
does not establish agreement.

EMO's identical full-prefix mean improves by **93.67%**, but its FP32 p99 is
0.0619595 and maximum is 0.259598. One of 2,048 token ratios lies outside
[0.8, 1.2]. The residual is concentrated in the math continuation: its mean is
0.00921297, and 177 response positions have error above 0.001, first appearing
at response token 142 and continuing intermittently through token 512. The other
three continuations have means between 0.00000252 and 0.00000294. This probe does
not determine whether the divergence comes from a routing boundary, kernel
ordering, or another implementation difference. The short cached result must not
be extrapolated to every longer trajectory.

## Serving timing

| Checkpoint | BF16 reference tokens/s | FP32 reference tokens/s |
|---|---:|---:|
| Non-EMO | 50.06 | 61.85 |
| EMO | 55.06 | 67.05 |

Timing counts the small warmed generation batch only. It excludes checkpoint
loading, compilation, warm-up and Core scoring. FP32 is faster within this tiny
eager-reference workload; this does not establish a production FP32 speedup.
The dtype can select different matrix kernels, and this reference implementation
has substantial overhead. The earlier graph-enabled production benchmark uses
a different response length and workload and is not a matched timing control.
FP32 doubles parameter storage relative to BF16; peak memory and training
backward/optimizer cost were not measured.

## What the FP32 baseline includes

- The same source checkpoint values are widened from BF16 to FP32, which is
  exact. No higher-precision checkpoint is substituted and no weights are saved.
- SGLang's eager compatibility path normally rejects FP32. A process-local
  diagnostic hook permits FP32 while retaining its other compatibility checks,
  and allocates the recurrent convolution caches in FP32. This is an experimental
  reference, not a supported production dtype switch.
- Core's pinned checkpoint loader assigns checkpoint tensors, replacing the
  factory-requested dtype. The probe therefore calls `model.float()` after
  loading. The first attempt to score Core failed the dtype audit and contributed
  no FP32 scores; its successful serving outputs were retained for the recovery.
- Runtime audits confirm 355 FP32 serving parameter tensors and 415 FP32 Core
  parameter tensors. Forward hooks reject BF16/FP16 tensors at module boundaries.
  This is a module-boundary audit, not an instruction-by-instruction audit of
  every custom kernel. Integer token IDs, routes and indices remain integer.
- All subprocesses use `NVIDIA_TF32_OVERRIDE=0`, `TRITON_F32_DEFAULT=ieee`, and
  `FLA_TRIL_PRECISION=ieee`. FP32 paths also select highest PyTorch matmul
  precision, disable CUDA/cuDNN TF32, and override FLA's explicit
  `chunk_intra.SOLVE_TRIL_DOT_PRECISION` to IEEE where present.
- Core verifies that every parameter's version counter remains unchanged during
  scoring. The checkpoint mounts are only read. No optimizer, backward pass,
  publication, or RL update is part of this experiment.

The BF16 and FP32 reference arms both disable prefill/decode graphs, radix cache
and overlap scheduling. Serving uses TP1, concurrency four, temperature/top-p
one, top-k disabled, ignore EOS, and one repeat. Core uses Torch full attention
and no router replay. The context bound is 4,096, with at most 16,384 cache tokens
and 16 recurrent-cache entries. FP32 serving reserves a 0.9 static memory fraction;
BF16 uses 0.65. Eight-token warm-up completions precede measured generation.

## Comparison with the LM-head-only study

The [LM-head study](lm-head-fp32-20260925.md) changes only the final projection
and measures modest improvements through graph-enabled fused-rounding serving.
This study uses the slower eager compatibility reference and stricter global
arithmetic controls. The cached workload is also shorter: four 64-token
continuations instead of 16 prompts, 512 tokens and two repeats.

The four-order reduction is measured against this study's matched BF16 reference,
not by dividing the earlier production-serving numbers by the new FP32 number.
The full-prefix control makes clear why changing the serving implementation is
a separate intervention. The machine-readable summary also retains cross-precision
comparisons and the earlier serving scores on the identical fixed prefixes.

The evidence supports investigating which precision-sensitive operations can
recover the agreement at acceptable cost. It does not show that every alignment
change improves learning, that existing BF16 learning is invalid, or that the
measured reduction transfers unchanged to long responses and updated policies.
A selective-precision change should first pass the same frozen-token comparison,
then a paired RL experiment should test its effect on reward and throughput.
