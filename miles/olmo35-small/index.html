    OLMo 3.5 Small (A4B) on B300

    Measured MILES RL layouts for OLMo 3.5 Small ("Hero Small", A4B, olmo35-small-e256k8-sh2x) on ai2/holmes B300 nodes. Configs: two-node-mech, four-node and eight-node. The current recipes use the Tiny batch/LR/loss baseline from PR #2271; historical measurements below used the earlier settings. They run four mechanics or 30 timing updates without checkpoints and do not establish learning quality.

    The maintained Small examples opt into FP32 vocabulary-head output for both the trainer and SGLang. The historical timings and H253 LR comparison used the default head precision.

    Model and start checkpoint

    • Start checkpoint: H203 SFT export /weka/olmo-3p5-post-checkpoints/abhishekr/a4b-gpu/a4bgpu-s34521/hf_step18410 (Olmo3MoeForCausalLM, bf16, 72.58B parameters / 145.16 GB).
    • 40 layers: 35 KDA plus full attention at layers 7, 15, 23, 31 and 39 (NoPE, head_dim 256); 256 routed experts top-8 (latent MoE dim 768, moe_intermediate_size 3072), shared expert, dense layer 0; hidden 1536; untied LM head.
    • Export notes: the emo_* fields are all null in this SFT export (the base export has EMo 8/256/256), so it is used as-is with no config edit. The HF config has vocab_size 100278 (LM head [100278, 1536]); 100352 is Core's padded size.
    • Data: robertb's H196 Dolci inputs (/weka/olmo-3p5-post-checkpoints/robertb/miles/h196-dolci-control-20261113/inputs/, 84,577 rendered rows). Its rendering was made for Tiny but uses the same tokenizer and chat template as this export. There is no held-out split, so do not set training.eval_interval.
    • Code verifier needs CODE_EXECUTION_TOKEN. Each recipe maps it to a placeholder Beaker secret name under [launch.secrets]; replace that name with a secret in the selected workspace. Never put the token value in the TOML. The historical timing runs omitted this credential: code samples were ungraded and their groups dropped (3-36 groups per update). Runs with code grading enabled have a different effective workload; remeasure throughput rather than assuming the historical timings apply.

    • Engine at R=224 (four-node example): 256 KDA slots; KV pool auto-sized to 3,919,232 tokens at mem_fraction_static 0.92; 19.7 GB free after CUDA graphs; full-attention KV peak 71%.

    Settings that matter

    • sglang_attention_backend = "trtllm_mha" for the 5 full-attention layers. On one engine with 96 forced 4K decodes: 2,881 tok/s vs 2,473 with triton. fa4 crashes the server: "SM100 forward with head_dim=256 does not support seqused_q/seqused_k".
    • Tuned fused-MoE tiles (SGLANG_MOE_CONFIG_DIR, see moe_configs): kernel -9% at batch 96, decode +1.6% at R=96. The tiles only take effect in an image built with this branch's configs/miles; an older image has no file at that path.
    • OLMO_SGLANG_CORE_COMPAT = "rounding". The attention trial's HF vs SGLang samples have mean |Δlogprob| 0.0155-0.0223 and argmax agreement 98.2-99.4%.
    • Admission R=224 on four nodes: sglang_max_running_requests 224, sglang_max_mamba_cache_size 256, sglang_server_concurrency 448, sglang_cuda_graph_max_bs_decode 224, producer budget async_max_concurrent_samples = 224 × engines, sglang_mem_fraction_static 0.92, no sglang_max_total_tokens key (RunSpec's default cap, R × context = 7,798,784 tokens, is above the 3,919,232-token memory-sized pool), and core.refresh_request_timeout = 3600.0 (see the timeout fix). The eight-node example stays at R=96 (128 slots, concurrency 192, graph bs 96, 3,342,336 KV tokens) with the same 3600 s timeout; R>96 is untested on 8 nodes.
    • Judge: timeout = 600 and chat_template = "qwen3-no-thinking". The judge bindings use the hashed verifier ids in the H196 verifiers.json.
    • two-node-mech enables the initial serving-weight comparison and repeats the standalone/training scoring check every update. These qualification checks add overhead relative to the original mechanics run and remain off in timing recipes (which retain the default startup scoring check).
    • The four/eight-node recipes request 4h/3h of protected runtime, respectively, based on historical startup and update times plus headroom, with an 8h timeout. Revisit these budgets when enabling code grading or other additional work.

    Topology interpretation

    • Four-node R96: trainer rollout-wait share is 35.5% of measured driver-stage time over u10-29. R64 increases it to 54.2%. The R96 trial delivers about 30.6K useful response tokens/s versus 22.4K for R64, a 37% improvement under the strict analyzer. Publication is about 9 seconds/update and is not the largest cost.
    • Eight-node R96: early compilation and slow trainer updates build a generation backlog. Median completed queue depth falls from 384 groups over u10-23 to zero over u24-29. Late trainer wait is 36.5%; doubling both trainer and inference capacity did not eliminate rollout starvation. Late stale-token discard fraction is 9.3% of delivered plus stale-discarded response tokens. Mean sample policy age has a per-update median of 8.0 versions in u10-23 and 4.9 in u24-29, versus 2.2 for four-node R96. These are different operating regimes.
    • Four-node R160: the later u30-49 window reduces wait to 24.9%, with median sample age 3.3 versions and no stale-token discards in that window. Its early near-zero wait is not a steady-state result. It failed the same final-drain boundary and was not repeated; the example moved on to R=224 with a 3600 s request timeout (see the timeout fix), which is also a single, unqualified run.
    • HTTP permit wait and generation-admission wait are zero at the median in these windows; unfinished work is near its configured budget. This does not isolate the judge's contribution. Rollout wait includes production, filtering and grading, and cannot be attributed entirely to policy GPU inference without more evidence.
    • Even the successful four-node R96 run drains for 741 seconds at shutdown and leaves 29.4M completed response tokens unused (10.5% of accounted delivered plus stale-discarded plus terminal-unused tokens). Warm-cycle throughput is not a complete job-cost metric.

    The optimization evidence supports the attention backend, tuned tiles and increasing admission above 64. It does not establish an optimal trainer/engine split. Compare longer runs with the same workload and objective, useful tokens per allocated GPU-hour, policy age, stale/unused work and judge time before selecting a production topology.

The serving geometry is the submitted timing4n-r224-t3600 (four-node) and timing8 geometry. Paths, credentials, runtime budgets and mechanics qualification controls also have the documented changes above.

    The completed-buffer factor stays four: 1,024 prompt groups / 8,192 responses. Unfinished producer budgets are 672, 5,152 and 4,512 for the two/four/eight-node layouts, respectively (0.328, 2.516 and 2.203 optimizer batches). The nominal sum of unfinished budget plus completed-buffer capacity is therefore 4.328, 6.516 and 6.203 batches. Finished siblings can live outside that accounting; these figures are not policy-age guarantees. Inspect measured age and useful throughput when tuning the new baseline. Do not copy Tiny's 12.5B inference preset, evaluator profile or cache geometry into Small: those are model-specific. Checkpoint/export/evaluation differences here are intentional for disposable timing runs, not a learning-run baseline.

    • Trainer: ~6.9K tok/s/GPU at EP8 on 4 nodes; ~6.0K tok/s/GPU with 2 × EP8; about 8.6-8.9M model tokens per update.
    • Response lengths are long: the median of per-update mean accepted lengths is about 8.1-8.4K tokens, truncation is 0-6%, and about 25% of groups are zero-std.
    • Startup to the end of update 0: 1,953-2,429 s on 4 nodes, 1,543 s on 8 nodes.
    • timing8 completed all 30 updates, then exited 1 at teardown because the final generation drain hit its 900 s timeout. Terminal refresh cleanup now cancels unused generation through the existing backend shutdown API before closing weight transport and disposing servers. This change has CPU runtime regression coverage; a clean Small GPU run is still required. Evaluation and final HF export retain their generation-drain boundaries because they may reuse live serving resources.

    The u40-49, r224, r256 and r224-t3600 rows come from the same artifacts via a separate analysis (engine rates are sampled engine means; r160 sampled 19 of 23 engines), not from the audit above.

    Request timeout at high admission

    At batch 1,024 (128 × 8), R=224 and R=256 raise engine throughput by 20% and 29% over R=160, but each request decodes more slowly: about 21.9 tok/s at R=160, 18.7 at R=224 and 17.5 at R=256. A 32,768-token response then needs about 1,750-1,870 s before queueing and refresh pauses, which exceeds core.refresh_request_timeout = 1800 s. Once the policy produces long responses (from about update 30), whole groups time out and are retried (883 timed-out group attempts for R=224 over updates 31-40, 622 for R=256 over 31-37; none at R=160). Updates became slower (medians 351/313 vs 241-247 s), truncated responses disappeared from training (0.7%/0.0% vs 3.6-3.8%), R=256 filled the KV pool (100%, 51 retractions) and aborted at update 37 of 40 when the rollout failure rate stayed above 50%.

    The fix is core.refresh_request_timeout = 3600.0 (the per-request deadline in refresh rollout; nothing else caps it). A timeout discards the whole group of eight, so a few slow 32K responses waste the other seven samples too. With 3600 s, R=224 (timing4n-r224-t3600, updates 31-40, 1-indexed; the table's u30-39) ran at 212 s/update mean vs 243 s at R=160 (-13%) and 401 s mean at R=224 with 1800 s: 0 timeouts, 0 stale drops, truncation 3.55% (r160 3.79%), and generation wait fell to 33 s, so the run is now train-bound. 4.7% of completed samples took 1,800-2,000 s end to end. Risk: the longest (>=30K-token) samples finish at policy lag 8-10 (median 9) against max_policy_lag = 12; if responses grow later in a long run, stale drops are the next limit. This was measured at batch 1,024; at the shipped 2,048 each update takes longer, so a sample should span fewer versions, but remeasure. The run completed 40/40 updates and then, on that pre-#2280 image (5c6645da), exited 1 when the final generation drain hit engine_drain_timeout (900 s). On main, terminal refresh cleanup cancels unused generation instead of draining (above), while evaluation and final HF export retain generation-drain boundaries. The four- and eight-node examples set engine_drain_timeout = 3600.0 to match refresh_request_timeout so those drain boundaries cover long responses when enabled (untested in a run). One run per arm; no seed repeat. The eight-node example keeps R=96 but also sets 3600 s, which only removes a failure mode.

    What did not work or was not tested

    • fa4 attention: crashes on head_dim 256 (above).
    • R=224 at the default 1800 s request timeout and R=256: slower than R=160 and failing on request timeouts (above); R=256 also fills the KV pool. R>96 on 8 nodes: untested.
    • R=64: slower (396 vs 302 s/update); engines gain throughput up to R=96. In single-engine forced decodes, R=144 matched R=96 and R=192 gave +19% total tok/s with each request ~40% slower.
    • EP4 trainer: untested.

    Code and runtime

    The original timing runs needed no Small-specific adapter or weight-sync changes. timing4 ran on image 01M7A0QM57N9499PGFAT73SMF0 (open-instruct a87a0feac). timing4n and r64 ran on image 01M7GA94Q6GKMP2MV2N36YE83Q, built from open-instruct 5c6645da. That is main 28c18166 plus an SGLang pin with an Olmo 3 sliding-window KV backport, which Small (no sliding-window layers) does not use. plan on main resolves the timing4n config identically to 5c6645da. These examples have not been run on an image built from main.

    Qualification before a learning run

    Copy two-node-mech.toml to ignored runs/, set a fresh output path and the actual workspace/secret names, then inspect python -m open_instruct.miles plan runs/small-mech.toml and python -m open_instruct.miles validate runs/small-mech.toml before using the committed-image launcher. Build the image from the revision being qualified; plan equality cannot establish runtime equality.

    Retain the Beaker experiment link, image ID, submitted TOML and completion artifacts. Verify all four updates, successful code grading, passing initial weight comparison, standalone/training score agreement, publication acknowledgments and a clean exit. Inspect refresh_scores for mixed-version responses and their historical-prefix and latest-forward log-ratio diagnostics; see Core diagnostics and mixed-policy refresh. Those ratios include policy drift and are not an isolated numerical-parity measurement.

    For publication debugging, enable core.diagnostic_interval = 1 with miles.check_weight_update_equal = true in the run copy to exercise the existing snapshot/reset/republish checks after optimizer updates. This adds a second transfer and extra gradient/update diagnostics. The check detects incomplete transfers over its selected tensors; it does not independently prove the export mapping. Keep a separate Core-versus-serving score comparison on identical tokens, prefixes and weights as a qualification requirement. HF-versus-SGLang greedy agreement and the always-zero train/ppo_kl do not establish that comparison.

    train/train_rollout_logprob_abs_diff (masked mean |trainer − rollout logprob|) is nonzero on every update, about 0.008-0.010 in the measured runs; collection_score_mean_abs is about 0.0065-0.0067. These combine numerical and policy differences and do not replace a controlled same-weight parity check. The metric that reads exactly 0 is train/ppo_kl, which is expected with use_rollout_logprobs = false (the old logprobs are recomputed by the trainer on the same weights) and refresh mode's one optimizer step per collection.

    Longer learning runs additionally need native checkpoint/save-resume and evaluation checks. The historical timing runs disabled saving; the current four-/eight-node starters enable bounded recovery saves. Their inputs still have no held-out split.

    Open items

    • R160 finished 50 updates, then failed its 900-second final generation drain. It used server concurrency 320, 192 KDA slots, CUDA graph batch 160, producer budget 3,680 and an auto-sized KV pool. Repeat after the terminal-cleanup fix and under the intended code-grading and batch/loss configuration.
    • Judge latency is not logged per call, so the judge's share of generation wait is unmeasured.

    Checkpoint settings in the current starters

    The four- and eight-node templates now enable 10-update native recovery saves, automatic resume, retention of the latest two saves and 50-update permanent milestones, plus a final native save. Their 30-update starting budgets therefore save at 10/20/30; 50-update retention becomes relevant when the run is extended. The four-update two-node mechanics check still disables checkpoints/resume. The reported historical timings used checkpoint-disabled runs and do not include this new save overhead or qualify restore correctness. Measure current batch 2,048 wall time and checkpoint cost, aim for recovery saves roughly every 1–2 hours, and verify the first save and resume before relying on these settings for long runs. See the shared checkpoint policy.
